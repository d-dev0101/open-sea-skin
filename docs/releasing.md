# Release guide

## 1. Prepare

1. Update the version in `package.json` and `extension/manifest.json`.
2. Run `npm ci` and `npm run build`.
3. Confirm `npm run check` reports that every generated install copy matches
   `shared/`.

## 2. Verify

Run the repository gates:

```sh
npm run check
npm run test:browser
npm run test:desktop
npm run package:extension
```

For native verification, integrate into the pinned Harness checkout, run its
Host and Client builds, start `pnpm dsh web`, and then run:

```sh
npm run capture
```

The capture job tests the sidebar launcher, live controls, persistence after
reload, and the wide-window Settings stacking regression before regenerating
the committed PNG/GIF gallery. Visually review every file in
`docs/screenshots/`.

## 3. Publish GitHub artifacts

Commit the source and generated gallery, push the tag `vX.Y.Z`, then create a
GitHub Release. Attach the extension ZIP generated by
`npm run package:extension`. Let the npm workflow below attach the package
tarballs after verifying registry integrity. Do not independently repack a
GitHub tarball after publishing npm. The tarball is the self-contained DSH marketplace bundle; the
repository source also contains the static and native-source installers.

Also attach a byte-identical copy named `open-sea-skin.tgz` to every release.
The marketplace uses `releases/latest/download/open-sea-skin.tgz`, so this
version-free asset must remain present when publishing a new version.

Release notes should identify the tested Harness commit, describe migrations,
and remind static-install users to run `install-skin.sh --update` after a
Harness upgrade.

## 4. Publish the DSH Desktop package

The repository root is also the npm package consumed by DSH Desktop's managed
plugin installer. It is deliberately public and has `publishConfig.access`
set to `public`; `prepublishOnly` rebuilds and verifies every generated DSH
asset before npm accepts the package.

For a manual first publish, authenticate with the npm account that owns the
package and run:

```sh
npm login
npm publish --access public
```

For repeatable releases, configure an `NPM_TOKEN` secret with package publishing
permission. Create a GitHub Release whose tag matches `package.json`, then
manually run `.github/workflows/npm-publish.yml` from main with that tag.
It is **manual only**, not triggered by release events or ordinary pushes.
The workflow builds and tests, packs once, publishes that exact tarball, checks
the registry SHA-512 integrity and SHA-256 byte equality, then uploads the same
versioned/unversioned tarballs with `SHA256SUMS`. Existing assets are not overwritten.

If npm publishing succeeds but a later step fails, do not republish the version.
Download its registry tarball, verify its `dist.integrity`, and recover the
GitHub assets from those exact bytes. Retain the workflow evidence artifact.
For an already published version, compare its GitHub asset and registry tarball:

```sh
npm view open-sea-skin@1.2.5 dist --json --registry=https://registry.npmjs.org > dist.json
node scripts/verify-release.mjs github.tgz registry.tgz dist.json
```

For users, recommend the exact npm package version first. If registry access
fails, use a verified local tarball; GitHub URL/tag installation can hit bundled
pnpm integrity errors and is not a reliable first choice.

## 5. Optional Chrome Web Store submission

Upload the same extension ZIP through a Chrome Web Store developer account.
The listing privacy answers are: no data collection or sale; no remote code;
`storage` saves preferences; loopback host access skins a locally running
Harness. Keep [privacy.md](privacy.md) linked from the listing and retain the
three.js MIT and Geist OFL notices in the package.
